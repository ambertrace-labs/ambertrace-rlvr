# Decision-corpus authoring correction — `decision_eval_v1` was not authored via a decision table

**Status (2026-10):** **methodology defect found + fix landed in code; corpus rebuild pending.** The
`decision_eval_v1` benchmark — and every result built on it — declared the decision vocabulary and its
restrictiveness *out-of-band*, decoupled from the platform's decision logic, with **no authored
decision table**. The current AmberTrace SDK requires a declared decision table and rejects the old
path. This note records the defect, the fix, and what it invalidates.

## TL;DR

- **Defect.** The decision corpus was generated by querying the oracle only for *verdicts*, while the
  verb set and the `restrictive`/`rank` metadata were declared locally (`vocabulary_from_verbs` /
  `--verbs` / `--restrictive`), independent of the platform. So "which verb is correct" came from
  AmberTrace, but "is that verb restrictive / which action is fail-open" was a local assertion that
  was never validated against the platform's decision logic. That is **using AmberTrace incorrectly**.
- **The SDK now forbids it.** In `ambertraceai>=2.10.0`, a domain declares its outcomes via a
  **`DecisionTable`** (`DomainCreate.decision_table`); the legacy `decision_vocabulary` is **rejected
  with HTTP 400** ("Declare outcomes with decision_table instead"). Each row (`DecisionTableRow`)
  carries `label`, `order` (ladder precedence), `permits` (may the action proceed — the authoritative
  fail-open/fail-closed bit), and `default`. The platform validates the table and computes verdicts
  against *that same table*.
- **Concrete hazard, demonstrated.** When a table is left *inferred* rather than declared, the platform
  fills `permits`/`order` by convention. In the loan proof-of-one it guessed `permits` **backwards**
  (`deny → permits=True`, `approve → permits=False`). Had we generated an eval set against that, every
  downstream fail-open / `severity_fail_open` / over-permit signal would have been computed against an
  **inverted** restrictiveness frame — exactly the "the verifier outputs differ from what you expect"
  failure.

## Proof-of-one: the correct pipeline, validated

A loan-approval domain authored the correct way (same policy as `decision_eval_v1` domain `d000`:
`deny if credit_score < 500 or monthly_payment > 0.80·monthly_income else approve`):

1. `domains.create(name, description)` + **declared** decision table via `domains.set_decision_table`
   (`applied=confirmed`, `provenance=customer`, `guessed=None`):

   | label | order | permits | default |
   |---|---|---|---|
   | approve | 1 | True | False |
   | deny | 2 | False | True |

   Ladder `order` runs *with* restrictiveness (higher = more restrictive — "the most
   restrictive fired row wins"), so `deny` is the highest-order, fail-closed default.
   `vocabulary_from_decision_table` therefore **inverts** `order → rank` (highest order →
   lowest `LabelSpec.rank`), because the repo's convention is "lower rank = more
   restrictive"; getting that inversion wrong would flip the over-permit/over-deny signal
   (caught in cold review).

2. `domains.build_ontology` (defines entities) → `platforms.create(..., verified_profile=True,
   verified_min_confidence=0.85)` → **platform `active`**.
3. `platforms.build_quality` → **`status=ok`**, all blocking checks green, including **faithfulness**
   ("the authored program faithfully implements the declared decision vocabulary — no orphan verbs"),
   **restrictive_coverage**, and **decision_class_reachability**.
4. Oracle verification — **4/4 certified verdicts match the policy** (the two deny triggers, credit and
   payment-ratio, both fire correctly).

So: domain + declared decision table → verified platform → oracle verdicts grounded in the *same*
validated table. Restrictiveness and verdict now share one source.

## The code fix (this change)

- **`vocabulary_from_decision_table(decision_table)`** (`eval_generator.py`) maps a platform decision
  table to the `LabelSpec` vocabulary: `restrictive = not permits` (missing `permits` → fail-closed,
  the safe default), `rank = order`; `partition` tables are equal-standing (no restrictiveness axis).
- **`decision_table_for_platform(api, platform_id)`** fetches the authored table and **refuses** to
  proceed if none is declared — an eval set is never generated against an inferred/guessed vocabulary.
- **`examples/generate_eval_set.py`** now reads the vocabulary from the platform's decision table; the
  out-of-band `--verbs` / `--restrictive` flags are removed.
- **`vocabulary_from_verbs`** is deprecated (retained only as a legacy shim for offline tests).
- SDK pin bumped to **`ambertraceai>=2.10.0`**.

## What this invalidates

The decision-domain results rest on `decision_eval_v1`, whose restrictiveness map was authored the
rejected way and was never validated against a platform decision table. Until the corpus is rebuilt
from correctly-authored platforms, the following should be treated as **not valid** and are flagged for
retraction/caveat:

- **Within-family decision contagion** (`within-family-decision-contagion.md`, #181) and its figures
  (#182).
- **The within-family HF adapters** (#183) — trained against the invalid ground truth.

Note this *supersedes* the earlier GRPO-degeneracy finding on `severity_fail_open`: that was a problem
*within* an already-invalid ground truth, so it no longer needs separate chasing.
